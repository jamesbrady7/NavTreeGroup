## 1. 背景：两代方案与架构约束

需求：一批同父的 `GuiBase*`，按自定义规则划分为若干组挂回原父亲，显示在同一棵导航树上；后来又加上排序、过滤——它们与分组同属"对原始数据的重新投影"。

**v1（GuiGroupingDemo）**：理想架构版（GuiBase=QObject、数据侧 unique_ptr 持包装），组做"展示层改嫁"（改 guiParent），靠 destroyed 信号联动生死。

**v2/v3（本工程）**：真实约束版——架构冻结：

| 约束 | 后果 |
|---|---|
| `GuiBase` 不是 QObject | 无 destroyed 信号，v1 的死亡联动整个失效 |
| 现有类不可修改 | 引擎只能是纯外挂，不能加 friend/虚函数/钩子 |
| 不许智能指针、不许动所有权 | 一切持有都是裸指针，悬空风险全靠自己防 |
| 三种所有权政体并存 | 节点死法不可预测，无法统一挂死亡通知 |
| 排序等逻辑已写死在导航树里 | 需要一条低风险迁移路径（第 12 章） |

结论：v1 的"写进树里"路线死了；v2 起改为"**叠在树上**"——引擎对现有对象**零写入**，分组（以及过滤、排序）只是可拆卸的投影。

## 2. 既有架构体检：三种所有权政体

同一个 GuiBase 家族，孩子归谁管、死时谁连坐，因类型而异：

| 政体 | 谁用 | 父子关系存哪 | 死亡连坐 |
|---|---|---|---|
| m_children | GuiBase 基类默认 | `m_children` | `~GuiBase` 逐个 delete |
| QObject | GeomObject 系 | `QObject::parent()/children()` | `~QObject` 级联 delete |
| 数据自管 | DataObject 系 | `m_supDataGroup`+`m_subDataGroups` | 各自析构自便 |

混用之雷：孩子同时进两种政体 = 双重删除（demo 的 `NamedGeom` 给出规范写法：QObject 政体的孩子只走 QObject 树，枚举虚函数重写为从 `QObject::children()` 取，`m_children` 恒空）。

**架构预留的两条接缝**（本方案的全部立足点）：

- **接缝①**：`visibleChildrenCount()/visibleChild()` 是虚函数且 DataObject 每次访问**现场重算**——活列表由数据侧自维护，死节点自然从枚举消失；
- **接缝②**：`parentForTree()` 是虚函数——每种类型自己回答"展示父亲是谁"（m_parentForTree / QObject::parent / m_supDataGroup），引擎只管调用。

一句话：**政体差异全部被虚接口吸收，引擎只消费枚举结果。**

## 3. 核心设计：惰性投影——组不存成员

没有信号、不能改类 → 任何"存成员指针"的方案必死（某个政体 delete 之后拿着悬空指针且无法察觉）。反转：

> **组不存成员。成员关系 = 规则 × 父亲当前活列表，现场重算。**

- `TreeGroup` 只是"票据架"（key/label/order），身上没有任何成员指针；
- 引擎为每个装过投影的父亲缓存一页账（`Projection`：flat 序列、组→成员、成员→组）；
- 缓存不是信仰：每次 `childCount()` 先拉活列表与 `lastLive` 做指针序列比对，变了就重跑流水线。

数据侧删节点的瞬间，它从活枚举消失 → 下次校验从所有组里**自动蒸发**。悬空指针不是被小心处理了，而是**构造上不可能被存下来**。

成本对齐：既有架构的 `visibleChildrenCount()` 本来就每次 O(n) 重算，引擎的 O(n) 指针比对与之同级，不引入新数量级。

零写入承诺：不改 `m_parentForTree`、不进 `m_children`、不碰数据侧容器。卸载引擎，树就是原来的树；老代码直接调 `visibleChild` 看到未投影的原始树——优雅降级，绝不崩溃。demo 每场景用"数据快照校验"（比对裸指针值）证明。

## 4. v3 核心：投影流水线（过滤→分组→排序）

看穿三种操作的本质，签名惊人一致——**都是"有序列表变换"**：

| 投影 | 对列表做什么 | 规则形态 |
|---|---|---|
| 过滤 | 删元素 | 谓词 `bool(GuiBase*)` |
| 分组 | 收拢 + 插入合成节点 | 键函数 `optional<GroupTicket>(GuiBase*)` |
| 排序 | 换顺序 | 比较器 `bool(a,b)` |

流水线：

```
live = rawChildren(parent)        原始事实(数据侧现场重算)
 → [Stage A 过滤]  spec.filter==false 的移出投影
 → [Stage B 分组]  按 key 归堆建组,组落在首成员原位置(复用旧组保状态)
 → [Stage C 排序]  对"组+直属"混合列表 stable_sort;组内成员同比较器
 = flat(模型看到的投影序列)
```

**顺序有语义，是设计决策不是实现细节**：

- 过滤在分组前：被隐藏的节点不在组里占成员位（否则出现"零件(4)"点开只见 2 个）；
- 排序在分组后：一个比较器同时管组间顺序（比 `ticket.order/label`）与直属顺序，不需要两套逻辑；
- `stable_sort`：判等元素保持数据侧原始顺序——枚举顺序本身可能是业务语义；
- 比较器**必须处理 TreeGroup**（排序面对的是混合列表）且是严格弱序 + 确定性 tie-breaker（如名字），否则投影抖动、视图闪跳。

一个 `ProjectionSpec` 声明全部意图，三个槽位都可为空（空 = 该阶段直通）：

```cpp
ProjectionSpec{ filter, grouping, less, opt };   // 一套 Spec = 一个父亲的完整投影定义
```

## 5. 类型系统：票据、规则、Spec、TreeGroup

```cpp
struct GroupTicket { std::string key, label; int order = 0; };
//  key=身份(相同归一组,空=逃生口不分组); label=外观; order=排序提示(供 less 消费)

using GroupRule = std::function<std::optional<GroupTicket>(GuiBase*)>;
//  纯函数契约:v3 里规则被流水线反复调用,比 v2 更是生死攸关

struct ProjectionSpec {
    std::function<bool(GuiBase*)> filter;    // 空=不过滤
    GroupRule grouping;                      // 空=不分组
    std::function<bool(GuiBase*,GuiBase*)> less;  // 空=保持数据侧顺序
    GroupingOptions opt;                     // collapseIfSingleGroup / dynamicAll
};
```

`TreeGroup`：继承 GuiBase（老代码可安全遍历），`parentForTree()` 返回 owner，成员枚举**委托引擎**（`visibleChildrenCount → engine.childCount(this)`），自身无状态。不进任何现有容器，生死由引擎独家管理。

`dynamicAll=true` 的价值在 v3 更突出：参与集 = 当前全部活孩子，数据侧新增节点下次校验自动进组/参与排序——**名单会过期，活列表不会**。

## 6. ITreeSource 窄接口与模型适配层

```cpp
class ITreeSource {   // 模型侧唯一依赖:只有读,没有写
    virtual size_t   childCount(GuiBase*) = 0;   // 唯一缓存校验点
    virtual GuiBase* child(GuiBase*, size_t) = 0;
    virtual GuiBase* parentOf(GuiBase*) = 0;     // 可能是组;逐层下钻 deepest-wins
    virtual int      rowOf(GuiBase*) = 0;        // -1 = 不在投影树上(被过滤/已死)
    virtual bool     isGroup(GuiBase*) const = 0;
};
```

为什么值得这一层（接口隔离 + 依赖倒置）：

1. **用类型系统守纪律**：模型拿到的引用上根本没有 `apply/install/bindSpec`——"读侧不许写"从 code review 纪律变成编译期事实；
2. **测试替身白送**：单测模型塞一个 FakeTreeSource 即可，不需要真引擎；
3. **编译防火墙**：模型只 include 二十行的接口头，引擎内部重构不惊动模型翻译单元；
4. **读写分窗**：写侧（业务层持 `TreeProjection&`）与读侧（模型持 `ITreeSource&`）看同一本账，各自最小权限。

代价：每查询一次虚调用——对导航树量级无感（rowCount 本来就在做 O(n) 枚举）。

## 7. NavTreeModel 与两条更新通道的信号协议

### 7.1 模型三要素全部问窄接口

```cpp
rowCount(parent)      → src.childCount(nodeOf(parent))
index(r,c,parent)     → createIndex(r, c, src.child(nodeOf(parent), r))
parent(idx)           → p = src.parentOf(n); p==root ? QModelIndex()
                                                 : createIndex(src.rowOf(p), 0, p)
```

`internalPointer` 仍存 `GuiBase*`（TreeGroup 就是 GuiBase，零特殊化）。**坐标铁律：row/parent 全部出自投影账本，绝不能用数据侧原始行号**——分组/过滤/排序后两本账必然不一致，用错的症状是视图错位、选中漂移、偶发断言。

### 7.2 通道一：精准删除（begin/endRemoveRows，事前坐标）

坐标必须在**死前**问（死后引擎就"忘记"它了）；`parentOf` 返回的可能是组；删的是组的最后成员时整组蒸发——信号要发在**组的位置**（外层一条，子树随组行消失，GUI demo Op2 实测就 1 条）。骨架四行（gui_demo 的 `removeWithSignal` 是完整范式，含级联预判与被过滤节点零信号分支）：

```cpp
GuiBase* par = engine.parentOf(victim);        // ① 死前问坐标(投影账本)
int      row = engine.rowOf(victim);           //    rowOf<0 = 被过滤 → 不发信号直接删
model.beginRowRemoval(par, row);               // ② begin(门面;beginRemoveRows 是 protected)
owner->destroySubDataGroup(victim);            // ③ 真删
model.endRowRemoval();                         // ④ end
// 级联预判:par 是组且 childCount(par)==1 → (par,row) 改报
// (parentOf(组), rowOf(组)),一条信号删整组行
```

数据变更被 begin/end **正确括号**，Qt 协议天然合法——Debug 版 `Q_ASSERT(last < rowCount(parent))` 也不会碰。迁移到内网时，只需把现有删除点里"取数据侧行号"的那几行换成 `parentOf/rowOf`，begin/删/end 骨架原样保留。

> **被否决的设计：TreeEditScope（事后快照 diff）**。曾做过一个"任意变更前后各拍一次投影快照、逐层 diff、自动发精确信号"的事务类（移除深→浅右→左、插入浅→深左→右）。看似魔法，实则与 Qt 的**事前协议**根本拧着：发 `beginRemoveRows` 时数据已经变了、真实 rowCount 已经缩小，Debug 版断言 `last < rowCount(parent)` 当场爆掉；要摁住它还得引入"发射窗口冻结 rowCount/index/parent 的相信账本"，补丁摞补丁。教训：**删除点在自己手里（拦得住）就用事前坐标；真拦不住的变更用 layoutChanged 或 reset 通道兜底**——不要为假想需求付真金白银的复杂度。

### 7.3 通道二：全量重建（reset + doItemsLayout）

```
model.beginFullReset()          // 模型暴露的公开门面(beginResetModel 是 protected)
→ wipe 旧子树(GeomObject 全删)
→ P.prune()                     // ★ 必做:批量 delete+new 是地址复用幽灵最高发点
→ rebuild 新子树
→ P.rebind()                    // ★ 谓词定位,Spec 自动重装(分组/过滤/排序一起重生)
→ model.endFullReset()
→ view->doItemsLayout()         // 你们既有流程的最后一步
```

reset 通道对引擎反而最友好：全量 reset 抛弃所有 index，无需坐标翻译。

### 7.4 局部更新（DataObject 持久，数据变了）

`P.refresh(node)` → 缓存对账自动收敛；视图侧用 `layoutAboutToBeChanged/layoutChanged`（配合 persistent index）兜底即可。

## 8. revalidate：引擎心脏

```
0. live = rawChildren(parent)          // 原始事实;与 lastLive 逐指针比对,相同→整条流水线跳过
A. vis  = filter(live)                 // Stage A 过滤
B. 分桶: vis ∩ 参与名单 → 按 key 归堆(逃生口: nullopt/空 key 留直属)
   塌缩检查(可选) → 按 key 复用旧组/建新组 → 淘汰未复用旧组(★级联拆内层投影)
   组内成员 stable_sort(less)
   重建 memberToGroup(只存本层账本,无全局反查表)
C. flat = 落位(直属原位,组在首成员位置) → stable_sort(less)   // Stage C 全局排序
```

幂等性由"缓存比对 + key 复用"共同保证：数据没变→命中缓存零动作；数据变了→重算，同 key 组**指针不变**（QModelIndex/QPersistentModelIndex 存活，展开/选中状态免 reset）。`refresh()` 只是"valid=false 再 revalidate"。

**"组在前"还是"组在首成员原位"？两者都对，是两道工序**：落位（buildFlat）永远把组放在**首成员原位置**——这是引擎的结构规则；但落位之后还有 Stage C 全局排序，**最终顺序由你给的 less 说了算**。demo 的比较器 `demoLess` 给组秩 -1（组前置），那是模拟"写死在旧导航树里的排序"（S10a 的对照组）；`less` 传空（或恒返回 false 的等价比较器，stable_sort 保持落位序）时，组就留在首成员原位。对照实验：unit T5（只落位不排序，组在首成员位）vs T6（sortFlat 后组前置）；tree_tabs Tab⑦ 三列并排（原始序/只排序/完整流水线）。

**流水线的每一段都抽成了 `pipeline.h` 里的纯函数**（不碰引擎状态、不 new/delete：`filterLive / bucketByKey / shouldCollapse / matchReusable / sortMembers / buildFlat / sortFlat`），`revalidate` 瘦身为编排器，只剩三件带所有权的事：建组、淘汰组（级联拆内层）、写账本。每块的"职责→输入→输出→校验"活演示见 `unit_tests` 的 T1~T6（引擎行为与模型层是 T7~T16）。

`rawChildren` 是多层分组的防递归关键：TreeGroup 的"原始孩子"= 到**外层** owner 投影解析成员（先校验外层再读表），递归终止于数据侧枚举；revalidate 内部只准用它，走公共 `childCount` 会 内层→组→内层 无限递归。

## 9. 多层分组：四种情形

1. **重复 apply 输入混着旧组**：展开为其当前活成员参与（否则静态白名单模式成员全体失踪）；
2. **不同分支各层独立**：每个父亲一页账（m_byParent），互不知晓；
3. **组内分组（三层）**：`childCount/child` 优先查节点自身投影（内层投影才是组当前的孩子）；`rawChildren` 防递归；实测 `root→[Parts]→[Steel parts]→零件` 三层 + 13 项不变量全过；
4. **级联销毁**：淘汰/ungroup 组时递归 `dropProjection`，否则内层子组泄漏 + 僵尸 key。

**被否决的设计**：全局"成员→组"反查表——多层下必然互相覆盖（Base 同属外层组与内层组，单层 map 谁写谁赢）。现行方案：`parentOf` 从数据侧自然父亲**逐层下钻**（每层查该层账本，能进组就继续钻），天然 deepest-wins，零全局状态。教训：**能用计算表达的层级关系，不要用扁平表缓存。**

5. **框选式多层分组（组作为成员，interactive_demo 的 J/K 实测）**：把"组 + 兄弟节点"一起框进新外层组。引擎侧四个配套改动：① revalidate 的参与名单 `parts = vis + 旧组`（旧组插在其首成员槽位），桶因此能收组；② `bucketByKey` 不再无条件跳过组——**是否收组由规则决定**：通用工厂规则（byKey/byPredicate）默认豁免组（防"TreeGroup 套娃"），手动规则显式按 label 收录；③ 淘汰名单排除"沦为成员"的旧组（它活在外层组里）；④ `buildFlat` 的落位代表 = 沿 memberToGroup 上溯的**最外层**组（Base→Steel组→外层组 ⇒ 本层只落外层组），且直属分支落旧组时必须登记 placed（否则复用指针被落两份）；⑤ `parentOf` 对组不再直接返回 owner，而是从 owner 走同一条下钻链（组可能是外层组的成员）。

## 10. 三政体生存法则 + 全量重建

TreeGroup 是引擎私产，不在任何政体的连坐名单里；owner 死后账本留下僵尸 key，**批量 delete+new（全量重建）时地址复用概率极高**，僵尸账会"幽灵附体"到新对象。三条腿：

| 腿 | API | 时机 | 机制 |
|---|---|---|---|
| ① 讣告 | `discard(node)` | 你能控制的销毁路径，delete 前 | 纯 map 操作删账+删孤儿组，绝不 deref 死者（它可能正在析构栈上，虚表已退化） |
| ② 剪枝 | `registerRoot` + `prune()` | install/refresh 边界自动 + 手动 | 从根沿**活枚举** DFS，走不到的 key=死者；死指针只作 map key 值比较，永不 deref |
| ③ 绑定 | `bindSpec(id, locate, spec)` + `rebind()` | 全量重建后 | 投影意图锚定**定位谓词**（名字/类型等稳定特征）而非指针 |

腿③两种命运（S9/GUI Op4 实测）：

- **持久 owner（DataObject）**：账页没死，rebind 命中缓存，**组指针跨重建稳定**（实测 before==after）；
- **一次性 owner（GeomObject wipe-and-rebuild）**：旧账被 prune，新对象被谓词重新命中，投影**自动重生**，重建代码零感知。

附赠能力：一条绑定管全树同类节点（`type()=="Folder"` → 所有文件夹获得同一套 Spec），未来新增的文件夹下次 rebind 自动入编——投影策略从"逐父 apply"升级为**声明式规则库**。

## 12. 从写死逻辑迁移的方法论

写死排序/过滤迁移的最大风险是悄悄改变用户看到的顺序。五步，S10a 就是第 2/3 步的活演示：

1. **盘点**：找出所有写死的排序/过滤点（多半藏在各 `updateVisibleChilren` 重写和模型 lessThan 里），每处翻译成比较器/谓词 lambda——会发现有些"排序"其实是过滤和分组的杂交，正好拆开；
2. **捕获**：迁移前 dump 每个父亲的原始枚举顺序与现行显示顺序，存基线；
3. **等价替换**：引擎只装 `less`（不过滤不分组），输出与基线**逐元素 diff**——`EQUIVALENT` 才说明翻译没走样；
4. **逐模块拔钉子**：确认等价后删写死代码，删一块跑一遍 diff；
5. 之后新需求只写 Spec / bindSpec，导航树代码零改动。

## 13. 踩坑记录

1. `qPrintable`=toLocal8Bit(GBK)，终端统一 UTF-8 用 `qUtf8Printable`（v3 起改 std::string+printf 亦可）；
2. 输入含组节点时成员丢失 → 展开为本父亲旧组的活成员；
3. 组内分组无限递归 → 私有 `rawChildren` 绕过自身投影；
4. `childCount(TreeGroup)` 优先级：自身投影 > 外层成员表；
5. 全局成员→组表在多层下互相覆盖 → 删表，parentOf 逐层下钻；
6. 级联销毁缺失 → dropProjection 自递归；
7. 双重删除雷：QObject 政体的孩子绝不进 m_children；
8. 僵尸投影地址复用幽灵 → discard + prune，全量重建通道 prune 必做；
9. `begin/endResetModel` 是 protected → 模型自己暴露 `beginFullReset/endFullReset` 门面（reset 通道属于模型层职责的体现）；
10. 事后快照 diff（TreeEditScope，已否决删除）撞 Debug 版 `Q_ASSERT(last < rowCount(parent))`——事后发射时数据已变、坐标与视图账对不上，"相信账本"补丁摞补丁。精准删除改**事前坐标**：死前问 parentOf/rowOf，四行骨架；拦不住的变更走 layoutChanged/reset；
11. `begin/endRemoveRows` 与 `begin/endResetModel` 一样是 protected → 模型暴露 `beginRowRemoval/endRowRemoval` + `beginFullReset/endFullReset` 门面；
12. header-only 的 Q_OBJECT 类：头文件必须**显式列进 add_executable 源列表**，AUTOMOC 才扫它（只扫 .cpp 及其同名头），否则链接缺 metaObject/qt_metacast；
13. MSVC：中文源码必加 /utf-8；嵌套花括号聚合初始化不吃，拆具名变量；
14. **跨政体摘除的 `nullptr==nullptr` 陷阱**（interactive_demo 实测炸出）：判断"子是否 QObject-父亲挂于 parent"时写 `child->QObject::parent()==dynamic_cast<QObject*>(parent)` —— 当 parent 非 QObject（Data/Mesh）时右侧得 `nullptr`，而挂在 m_children 里的 Geom 子其 QObject 父亲**也是** nullptr，`null==null` 误判成立 → 走"只 delete 不 removeTreeChild"分支 → 子仍留在父 m_children 成悬空 → 父析构二次 delete 崩溃。修正：**必须先判 `dynamic_cast<QObject*>(parent)!=nullptr`** 再比 QObject 父亲。教训：混合政体销毁里，"两个都空"绝不等于"父子相属"；
15. **walkBindings 绝不能对组节点求值绑定谓词**（interactive 实测：组 label 与 locate 特征同名时崩在 operator new）：命中 → 对组装投影 → 组成员又被同规则分出内层组 → 内层组 label 仍同名 → **无限嵌套**直到栈/堆耗尽。修正：`if (!isGroup(n) && b.locate(n))`。绑定描述数据节点，组是投影产物；
16. **parts 里的旧组可能是本轮已 delete 的**（S2 实测 UAF）：换规则淘汰旧组时，若其成员还活着，旧组仍占 parts 槽位 → buildFlat 把野指针推进 flat。修正：cull 时记录 `deleted` 集合，落位前从 parts 剔除；
17. **Qt 关键字宏与 CRT 报告 API 两个名字坑**：变量绝不可叫 `slots/signals/emit`（QObject 头把它们 define 成 Q_SLOTS 等，声明静默变垃圾、报错报在使用处，极难查）；`_CrtSetReportMode/File` 第一个参数是**单一**报告类型而非位掩码，传 `(_CRT_ASSERT|_CRT_ERROR|_CRT_WARN)` 会触发 CRT 自身断言弹窗、把真正的崩溃点盖住；
18. **buildFlat 直属分支落旧组必须查 placed**（interactive 实测：重建后重复节点、两行同 internalPointer 点一选一）：多层结构下外层组先作为"后代成员的代表"被落位（面网格→rep=外层组），迭代到该组自身（它在 parts 里占首成员槽位）时若不查 placed 就再 push 一遍 → 同指针进 flat 两次。修正：直属分支遇已 placed 的组 → `continue`；
19. **"直接成员全是组"的组会从参与名单失踪**（用户最简复现：手动组1={Origin,BoltB,Cover}→手动组2={手动组1,钢件}→手动组3={手动组2,标准件}，第三步手动组2 收不进、手动组3 只挂上标准件）：槽位计算只看组的**直接**成员是否在 vis 里，而手动组2 的直接成员是两个组 → 拿不到槽位 → 不进 parts → 外层规则看不见它。连带两处同源缺陷：matchReusable 的旧组名单只取顶层 `p.groups`（嵌套组无法被复用 → 重算即孤悬泄漏）、`p.groups` 只记顶层桶（嵌套组下轮认不出）。修正三件套：槽位**传递式下钻**到首个 vis 可见后代；复用/淘汰名单 = 旧账**全层**组；`p.groups` = flat 顶层组 ∪ 成员表全部组键。教训：**账本的"组清单"必须与"成员表"同视野（全层），任何只扫一层的名单都会在第三层嵌套时露馅**（interactive P 步为永久回归）。

20. **递归 DFS 有深度上限**（bench deep 实测：10 万级深链上 `prune` 的 `collectReachable` 爆栈崩溃）：引擎自身不能赌调用方栈大小（1 MB），`collectReachable` / `walkBindings` 全部改成**显式栈迭代**。⚠ 但 **`~GuiBase` 的连坐析构是数据类自己的递归**，深链 `delete root` 一样爆栈——这是冻结架构的属性，与引擎无关（生产树深 <100 无虞），真有超深链就调 `/STACK` 链接器储备或自底向上拆；
21. **`install` 内嵌全树 prune**（bench 实测：1 万个内部节点逐个 install ≈ 20 分钟，走 `bindSpec+rebind` 一次 ≈ 0.5 s）：批量装配**必须**走声明式绑定，绝不 N×install；
22. **`rowOf` 里逐位调 `child(p,i)` 是复合二次方**（wide 实测：单次 rowOf **0.46 s** = O(组员数 × 父亲孩子数)，因为每一位都触发一次完整缓存校验、组路径还要顺带 revalidate owner 的 20 万孩子列表）：改成"就地取账本序列扫一遍"，整次 rowOf 只校验一次，回到 O(兄弟数)；
23. **组页 revalidate 会连锁拆掉自己**（`freshMembers(g)` 触发 owner 重算 → owner 可能恰好淘汰这个组 → `dropProjection` 顺手拆掉本页 → 调用点手里的 `Projection&` 悬空）：所有"revalidate 之后继续用 pit/p"的调用点都必须**回查 `m_byParent.find()`**；
24. **`std::unordered_set` 不适合做百万级指针去重**（bench pbreak 实测：244 ns/节点，是"走树"本身的 11 ns/节点的 **22 倍**）：节点式存储每次 insert 一次 malloc + 逐级小步长扩容反复 rehash + 指针低 4 位恒 0 导致分布不可控。自研 `ptrset.h`（开放寻址 / 线性探测 / 2 倍翻倍 / 零节点分配）降到 **50 ns/节点**；
25. **以指针为键的位图/表，一律定长，永不按需扩容**：splitmix64 输出接近 2^64，`while (cap < need) cap <<= 1` 会一路涨到 `std::vector::resize` 抛 `length_error` → `abort()`（实测五个 demo 全崩在这里）。先截断哈希再定位（本工程用 2^23 位 = 1 MB）；
26. **`std::map` 在读侧热路径上是纯浪费**（`[Q]` 实测：10k 键随机查找 map 96 ns vs unordered_map 17 ns，红黑树每一级都是一次可能 cache miss 的指针追逐）：`m_byParent` / `m_groupOwner`（10 万条）/ `memberToGroup`（100 万条）全部换 `unordered_map`。换得安全的两个理由：① unordered 容器 rehash **只失效迭代器、不失效元素引用与指针**（节点式容器），所以 `revalidate` 一路持有的 `Projection&` 不受影响；② 全库对这三张表的遍历全是顺序无关的（`p.members` 因遍历顺序参与组账本构建，刻意保持 `std::map` 不动）；
27. **"缓存命中"不等于"不用看数据"**：`rowOf` 先 `parentOf` 下钻、再对同一页 `revalidate` 一次，同一次查询里同一页被校验 2~3 次（组页更甚——组 revalidate 内部还要回头校验 owner）。引入**查询纪元**（`m_queryEpoch` + 页内 `checkedAt`，每个公开操作入口开 `EpochScope`，**只有最外层递增**，否则 `rowOf`→`parentOf` 会把优化抵消）：同一次操作内一页只校验一次，跨操作必递增 → 一定重新枚举。⚠ 前提是"数据侧变更必然经过引擎 API 或与引擎无交互"——**若模型跨线程/异步改数据树，删掉 `EpochScope` 即可退回全枚举，行为完全不变只是慢**。配套：强制重算处（`installInternal`/`refresh`）必须把 `checkedAt` 一起清零，否则 `valid=false` 仍被闸门短路；
28. **加速缓存的失效方向必须选安全的那一边**（提示位图实操）：`m_pageHint`/`m_groupHint` 只置位、**从不清除**，所以只会往"多算"方向撒谎（白探测一次，无害）；真正危险的是**漏置位**——账页存在却没提示 → 被跳过 → 子树不可达 → **活页被当僵尸删**。因此置位义务必须收敛到**唯一创建点**（`projection()` 与唯一的 `new TreeGroup`），审计这两个点即可覆盖全部风险；
29. **加速门控绝不能跳过语义动作**：`walkBindings` 里那道"这节点没账页也不是组就跳过"的门控，若放错位置（放到绑定谓词之前）→ `locate` 永不对该节点求值 → 谓词命中却没账页的节点永远装不上投影 → **五个 demo 全崩**。门控只能用来跳过**探测**，不能跳过**语义**；
30. **性能问题先做 A/B 归因**（方法论，本轮全部决策的依据）：bench 的 `pbreak` 场景把 prune 拆成"纯数据侧 DFS / +unordered_set / +PtrSet / 引擎实测"四行，一眼看出 **A(走树) 只有 11 ms 而 D(引擎) 有 124 ms** —— 于是钱全花在去重集、查表结构、否定探测上，而不是去优化 DFS 本身。**"某操作慢"和"该操作里哪一步慢"是两个问题**，先分清再动手；
31. **★ 读侧（`childCount`==`rowCount`）曾经会 `delete` 展示节点 —— UAF 契约漏洞**（外部 review 用探针实证，本工程已修）：`childCount → revalidate → 淘汰 → dropProjection(g); delete g;` 全程零信号。而 `QTreeView` 对**每个展开的组**持有 `QPersistentModelIndex`，其 `internalPointer` 正是那个 `TreeGroup*` —— 释放即 UAF，视图完全不知情。探针原样复现：裸删成员后只问一句 `P.childCount(root)`，`liveGroupCount` 从 1 变 0。**根因是"调用方纪律"冒充"引擎保证"**：所有 demo 之所以没炸，是因为每个结构变更都被 `beginFullReset` 包住了。修正：`m_retired` 待回收队列（**只置不删**，把 UAF 降级为"读到过期状态"）+ `collectGarbage()`（唯一真正 delete 的地方）+ `ITreeSource::collectGarbage()` 进窄接口（模型层职责，不是业务刀把）；`NavTreeModel` 的 `endFullReset`/`endRowRemoval` 自动调用 → 走这两条通道的调用方零心智负担。⚠ 回收时机**不能**顺手放进 `prune`（它可能在视图仍持有 persistent index 时被调用）；
32. **★ 组对象会被地址复用**（外部 review 实证，本工程已修）：`TreeGroup` 是引擎自己 new/delete 的，`delete` 后下一个同 key 的组**必然**可能拿到同一地址（探针实测 `0x...D26140` 完全复用）。于是旧的 `QModelIndex.internalPointer` 静默误认新组 —— 视图不崩，但展开态/选中被错误继承，而两者成员集完全不同。修正同坑31（不 delete 就没有可复用的地址），interactive **Q 步**钉死。教训：文档把"地址复用幽灵"列为头号风险，但**没有任何检查覆盖"组"这一类**（原 bench dbg 只测叶子节点）；
33. **★ `valid` 是承诺，必须在流水线跑完才置**（异常安全）：曾把 `p.valid = true; p.checkedAt = ...` 写在 `rawChildren` 之后、流水线之前。用户 `filter/grouping/less` 一抛，缓存就说谎 —— 下次 `childCount` 短路返回**上一次**的 `flat`，而那份 flat 里可能含已被 delete 的对象的野指针。修正：`valid`/`checkedAt` 挪到函数**最末尾**（`sortFlat` + 组账本写完之后）。中途抛异常则本页停在 `valid=false` → 下次重跑整条流水线 → 自动收敛。代价：异常后多跑一次流水线；收益：任何比较器抛异常都不会污染账本；
34. **★ 级联预判必须沿 `parentOf` 向上循环，不能只判一层**（外部 review 指出，本工程已修 + T19 专项回归）：三处 demo（`gui_demo`/`interactive_demo`/`tabs_demo`）都写着 `isGroup(par) && childCount(par)==1`。但多层分组下，内层组蒸发会让外层组也空 → **视图里消失两行，只发一条信号** → 模型 `rowCount` 与视图对不上（失步）。修正：`navtreemodel.h` 提供共用的 `cascadeTarget(src, victim)`，沿 `parentOf` 连续检查并返回**最外层**会蒸发的组；一旦某层存活就 `break`（成员数只减不增到 0，上面的层一定也存活）。⚠ 另一条自检教训：Q 电池最初依赖 O/P/N 步的深层嵌套状态做前置，两次因"中间状态不对"而误报 —— **回归用例要用自包含小树**，否则测的是电池自己；
35. **惰性投影无法避免"纯读改变树形状"**（架构固有事实，不是 bug）：成员被数据侧删掉 → 组空 → 组蒸发 → 行数变，而模型收不到任何信号。修好内存安全（坑31）**不等于**修好坐标失步。引擎为此提供 `structRev()`（形状版本号，进 `ITreeSource`）：调用点在精准操作前后各取一次，不等即说明结构被动过、坐标已失步、应改走 reset 通道。这是给使用方的**契约自检工具**，不是引擎能自动兜住的事；
36. **★ `QAbstractItemModelTester` 查不出"信号发错行"——它的检查边界被误解了**（实测推翻原有论断，T18 已按正确方式重写）：Tester 检查 `index/parent/rowCount/data` 的互逆性与信号配对，看起来正好该覆盖"信号发错行"，但**它做不到**：`rowCount()`/`index()` 每次都重新问引擎拿**当前真实结构**，所以"模型报告的结构"永远自洽；而"发出的信号与实际变化是否匹配"完全不在它检查范围内。注入实验铁证：故意把组蒸发发成组内成员行删除（诊断显示 `isGroup(par)=1, childCount=1`，组必蒸发），Tester 仍报"全程无断言"。⚠ **同源的第二个陷阱**：也别用"删除前后 `rowCount` 差值"来验证 —— 它每次重问引擎，差值恒等于真实减少量，与信号对错无关（我第一版就是这么写的，实测反例照样"通过"）。**唯一有效的做法是捕获 `rowsAboutToBeRemoved` 的参数本身**，断言 `(parent, first, last)` 等于 `cascadeTarget` 算出的组行坐标。T18/T19 已按此重写，并各带一条**分辨力自检**（证明单层判法会给出不同答案 → 断言非恒绿）；
37. **★ 造多层嵌套必须靠"两次 install + rule 只收指定 key 的组"**（T19 实操，与 demo 的 `installGrouping` 同范式）：分组规则作用在 `parts = vis + 旧组` 上 —— 组能被收进桶**靠的是旧组参与 parts**，而不是 `rawChildren` 里出现组（组的成员表里只有数据节点）。所以正确顺序是：① 第一次 install 让数据节点成组（Inner）；② 第二次 install 时 Inner 作为旧组参与 parts，被 rule 收进另一个桶（Outer）。⚠ 两个必踩的坑：rule 必须**只收 `key=="Inner"` 的组**，否则 Outer 会把自己也收进去 → 无限套娃（这正是工厂 `byKey`/`byPredicate` 无条件豁免组节点的原因）；定位内层要用 `parentOf(数据节点)` 逐层上问，**不能按名字扫一层**（Inner 已在 Outer 内，扫一层必然找不到 —— 这个坑我连踩两次）。

## 13.5 性能实测（百万节点）

完整数据、复现命令、优化清单与 A/B 证据见 **`docs/性能实测_百万节点.md`**。三条最该记住的：

- **全量重建 ≈ 0.93 s、全树展开 ≈ 0.76 s、单次查询 2.2 µs、峰值内存 300 MB**（1M 数据节点 + 10 万组）；

- **生产纪律②`prune`/`rebind` 是全树 DFS（~120 ms/百万节点），别进帧循环或每行绘制路径**。

### 14.2 itreesource.h（全文）

```cpp
#pragma once
// ═══════════════════════════════════════════════════════════════
//  ITreeSource:展示树的只读窄接口(模型侧唯一依赖)
// ═══════════════════════════════════════════════════════════════
//  目的:QAbstractItemModel 只认识这四个查询,拿不到投影引擎的写侧刀把
//  (apply/install/bindSpec/prune...),用类型系统守住"读侧不许写"的纪律。
//  契约:调用节奏与 Qt 模型一致 —— 先 childCount(触发缓存校验),
//  再 child(直接读缓存);四件套的答案永远出自同一本账(投影),
//  parentOf/rowOf 与 childCount/child 互为逆运算。
#include <cstddef>

class GuiBase;

class ITreeSource {
public:
    virtual ~ITreeSource() = default;

    virtual size_t   childCount(GuiBase* node) = 0;   // 投影后的孩子数(含组节点)
    virtual GuiBase* child(GuiBase* node, size_t i) = 0;   // 投影序列第 i 个
    virtual GuiBase* parentOf(GuiBase* node) = 0;     // 投影父亲(可能是组;逐层下钻 deepest-wins)
    virtual int      rowOf(GuiBase* node) = 0;        // 在投影父亲序列中的行号;-1=不在投影树上(被过滤/已死)
    virtual bool     isGroup(GuiBase* node) const = 0;
};
```

### 14.7 成员变量速查表

三层各成员的**作用**与**读写时机**（与代码内注释同步）。

**数据侧（guibase.h）——"事实"**

| 成员 | 作用 | 什么时候被使用 |
|---|---|---|
| `GuiBase::m_parentForTree` | 展示树"显式父亲"提示位，非所有权 | 构造写；`parentForTree()` 第一优先级读。三政体下常为 null（DataObject 回退 `m_supDataGroup`、GeomObject 回退 QObject 树）。**引擎从不写它** |
| `GuiBase::m_children` | GuiBase 政体孩子容器，带所有权（`~GuiBase` 连坐） | `addTreeChild/removeTreeChild` 写；默认版 `visibleChild*` 读。QObject 政体孩子绝不能进这里（双重删除雷区） |
| `GuiBase::m_visibleChildren` | 可见孩子**缓存暂存区**（非账本） | 基类不碰；DataObject 每次访问 clear+重填。引擎透过虚函数总读到最新值 → "死节点蒸发"的物理基础 |
| `DataObject::m_supDataGroup` | 数据侧父亲（真实所有权方），兼任 `parentForTree()` 回退 | 构造写；`parentForTree()` 回退读 |
| `DataObject::m_subDataGroups` | 第三政体：DataObject 自管子数据组 | `addSubDataGroup/destroySubDataGroup` 写；`updateVisibleChilren()` 枚举读。`rawChildren` 透过虚函数看到的就是这份名单 |
| `DataObject::m_subDataItems` | 子数据项，按草图语义不进 visibleChildren | demo 闲置，忠实还原架构 |

**引擎侧（treeprojection.h）——"账本"**

| 成员 | 作用 | 什么时候被使用 |
|---|---|---|
| `TreeGroup::m_ticket` | 组身份三件套 key/label/order | 构造写；`revalidate` 按 key 复用旧组（key 同 → 指针不变 → UI 状态跨刷新存活）；labeler 与 less 读 |
| `TreeGroup::m_owner` | 原父亲（挂载点），非持有 | `parentForTree()` 返回它；`rawChildren(组)` 靠它找外层投影。owner 死后变野指针，但引擎只做 map key 值比较、**永不 deref** |
| `Projection::spec` | 本页投影定义（filter/grouping/less/opt） | `install/bindSpec` 写；`revalidate` 每次消费；`refresh`=旧 spec 重跑 |
| `Projection::pool` | 静态参与名单（dynamicAll=false 时） | `install(siblings)` 消毒后写；分组阶段做 `vis ∩ pool` |
| `Projection::lastLive` | **缓存钥匙**：上次的原始活列表快照 | `revalidate` 第 0 步指针序列比对，一致 → 整条流水线跳过。数据侧删节点被自动发现的机制 |
| `Projection::flat` | 流水线最终产物（组+直属混排，已排序） | `revalidate` 末尾写；`childCount/child/rowOf` 读 —— **模型行号唯一来源** |
| `Projection::groups` | 当前生效组列表（引擎唯一所有） | `revalidate` 重建；未复用旧组在此 cull（级联拆内层投影）；`uninstall/析构` 删组 |
| `Projection::members` | 组 → 活成员（已排序） | `revalidate` 写；`rawChildren(TreeGroup)` 读 —— **组成员关系唯一存储处**，组对象零成员指针 |
| `Projection::memberToGroup` | 成员 → 组（**仅本层局部**，无全局版） | `revalidate` 写；`parentOf` 下钻读，命中 → 组，不命中 → 自然父亲（deepest-wins）。全局版在多层分组下会互相覆盖（v2 踩坑） |
| `Projection::valid` | 账页已算标记 | `revalidate` 置位；`child()` 读 flat 前检查 |
| `TreeProjection::m_byParent` | **总账本**：装过投影的父亲 → 账页 | 一切查询第一站：`childCount` 先查自身投影（组里再分组的优先级）、`parentOf` 逐层查、`hasProjection`。key 可能是死指针（僵尸/幽灵），靠 discard/prune 清，清理只值比较 |
| `TreeProjection::m_groupOwner` | 组 → 原父亲全局登记 | `revalidate` 建组写；`rawChildren(TreeGroup)` 找 owner；`prune` 释放孤儿组 |
| `TreeProjection::m_roots` | 注册树根，prune/rebind 的 DFS 起点 | `registerRoot` 建树后写一次；prune/rebind 从根沿活枚举走可达集，走不到的 key 即死者 |
| `TreeProjection::m_bindings` | 声明式绑定表（id+locate+spec） | `bindSpec` 追加（同 id 去重）；**`rebind()` 全量消费**：prune 后 DFS，活节点跑 locate 谓词，命中且没装 → 装。意图锚定谓词而非指针 → wipe-and-rebuild 后自动重生 |

**模型侧（navtreemodel.h）——"翻译官"**

| 成员 | 作用 | 什么时候被使用 |
|---|---|---|
| `NavTreeModel::m_root` | 不可见根 | 构造写；`nodeOf(无效index)` 返回它；`parent()/indexFor()` 里 `p==m_root → QModelIndex()`（不可见根规则） |
| `NavTreeModel::m_src` | ITreeSource 窄接口引用，模型对引擎的全部认知 | 每个 override 都用它（index→child、parent→parentOf+rowOf、rowCount→childCount）；类型是接口 → 写侧刀把拿不到（编译防火墙） |
| `NavTreeModel::m_labeler` | 节点 → 显示文本注入函数 | `setLabeler` 写；`data(DisplayRole)` 读 |

一句话串联：**数据侧成员是"事实"（三个容器三种政体），引擎成员是"账本"（lastLive 校验、flat 是答案、members/memberToGroup 是组的唯一存储），模型成员只是"翻译官"（坐标全问 m_src，一个指针都不自存）**。悬空指针结构性消失的根因：没有任何一层长期持有"会被别人 delete 的指针"当真相 —— 账本随时可撕了重算，重算只需要规则 × 活列表。
