# 部署手册 —— 导航树投影引擎接入手册

> 面向:第一次把本引擎接进自己工程的人。
> 目标:照着抄就能跑;每个场景都给"该调什么 / 不该调什么 / 为什么"。
> 配套:契约与证据见 `PROJECT.md`;设计原理见 `设计精讲.md`;可跑样例见七个 demo
> (`navtree_demo` 引擎行为 / `gui_demo` 两条更新通道 / `interactive_demo` 场景全集)。

---

## 0. 三十秒心智模型

```
数据侧的树（你的）                    展示树（引擎加工出来的）
─────────────────                    ──────────────────────
GuiBase 三政体原始枚举   ──投影──▶   filter → 分组 → 排序 的结果
        │                                    │
        │  ① 你改了数据，就【告诉引擎】        │  ② 引擎算出展示树
        ▼                                    ▼
   invalidate / notifyRemove / invalidateNode        childCount / child / parentOf / rowOf
                                                     （窄接口 ITreeSource）
```

一句话规则:

> **引擎不偷看你的数据。你改了数据，必须自己告诉它。**
> 忘了告诉它，它不会崩，只会**继续显示旧的**（Release 下静默陈旧）。

### 本文代码段的阅读约定

- 引擎接口是**真实的**（`TreeProjection` / `NavTreeModel` / `ProjectionSpec` / `GroupRules`），可直接抄。
- **`PartObject` / `FolderObject` 是 demo 的节点类**，换成你自己的派生类即可（引擎只依赖 `GuiBase`
  的三个虚接口：`visibleChildrenCount` / `visibleChild` / `parentForTree`）。
- 形如 `collectChildren` / `destroyNode` / `attachNewChild` / `displayName` / `isRelevant` 的函数是
  **占位**：它们属于你的数据层（三种所有权政体各有各的销毁/挂载规矩），引擎不管这些。
- 本文所有片段都能在 demo 里找到对应的**完整可跑版本**（见 §13）。

## 1. 最小接线(五步)

```cpp
#include "guibase.h"            // 你的节点基类（冻结架构，不要改语义）
#include "treeprojection.h"     // 引擎
#include "navtreemodel.h"       // QAbstractItemModel 适配层
#include "projection_stages.h"  // 只有你自己写流水线阶段测试时才需要

// ① 拿引擎（进程级单例，整个进程一套）
TreeProjection& P = TreeProjection::instance();

// ② 注册你所有树根 —— prune/rebind 的 DFS 起点。不注册 = 僵尸账页永远清不掉。
P.registerRoot(root);

// ③ 声明式绑定：告诉引擎"哪些父亲要装投影、装成什么样"
TreeProjection::SpecBinding binding;
binding.id = "parts-by-material";                        // 绑定 id，重复 bind 会覆盖

binding.locate = [](GuiBase* n) {                        // 现在指针是谁 → 谓词要能重新认出它
    return dynamic_cast<PartObject*>(n) != nullptr;      // 命中就给它装一页
};

binding.spec.filter = [](GuiBase* n) {                   // 可选：false = 移出投影
    auto* p = dynamic_cast<PartObject*>(n);
    return !(p && p->suppressed);
};
binding.spec.grouping = GroupRules::byKey([](GuiBase* n) {   // 可选：返回空 key = 不分组
    auto* p = dynamic_cast<PartObject*>(n);
    return p ? p->material() : std::string();
});
binding.spec.less = nullptr;                             // 可选：空 = 保持数据侧顺序
binding.spec.opt  = { /*collapseIfSingleGroup=*/false, /*dynamicAll=*/true };

P.bindSpec(std::move(binding));                          // 内部立刻生效（含一次全树定位）

// ④ 模型只吃窄接口（拿不到写侧刀把，误用被类型系统拦住）
NavTreeModel model(root, P);
model.setLabeler([](GuiBase* n) { return QString::fromStdString(displayName(n)); });

// ⑤ 挂进视图
view->setModel(&model);
```

**三条不许做的事：**

| 不许 | 为什么 |
|---|---|
| 不要让模型/其它模块直接调 `install/uninstall/apply/prune` | 那是写侧；模型只该拿 `ITreeSource`（已用类型系统隔离） |
| 不要改 `GuiBase::m_parentForTree` 来"实现分组" | 引擎**零写入**纪律；分组只作用于展示树，不进数据树 |
| 不要自己 `delete` `TreeGroup*` | 组是引擎私产，只有引擎的回收点能释放 |

## 2. 你改了数据之后该调什么（**最重要的一张表**）

| 你做了什么 | 必须调 | 漏掉的后果 |
|---|---|---|
| 父亲的孩子列表变了（增 / 删 / 移动 / 重排序） | `P.invalidate(parent)` | 静默陈旧（有兜底，见下） |
| 删掉一个节点（**在 `delete` 之前**） | `P.notifyRemove(它的数据父亲, victim)` | 同上 |
| 改了节点**属性**（材质 / 名字…一切影响 filter/grouping/less 的值） | `P.invalidateNode(node)` | ⚠ **永久陈旧，没有任何兜底** |
| 大改动，懒得逐个报 | `P.invalidateAll()` | 同上（但一定能在下次读收敛） |

**兜底能力的差别（这一条是 C5 里最容易被误读的）：**

- `invalidate` / `notifyRemove`：**有兜底** —— 引擎在 `prune`/`rebind`/`install`/`refresh`
  这些"卫生边界"会用 `healIfDrift` 比对"孩子列表"来自愈；Debug 下 `childCount` 还会当场点名。
- `invalidateNode`（属性变更）：**没有任何兜底** —— 三层兜底比的都是**孩子列表**，
  而属性变更不改变孩子列表 ⇒ 一层都发现不了 ⇒ **投影会永久停在旧状态**，
  直到某次 `install`/`rebind`/reset 才被动修正。**所以它是硬契约。**

> **上线建议**：首发把漏报检测打开，它就是 Release 下唯一能发现"漏了通知"的手段：
> ```cpp
> P.setParanoidChecks(true);   // 代价：每次 rowCount 多一次枚举（导航树按"每个父亲问一次"访问，可接受）
> ```
> stderr 会点名"哪个 owner 漏了 invalidate"。稳定后按名单逐处补，再关掉。

## 3. 场景：**一个父节点下的子结点全部删掉，然后重建**

这是"整页换血"。**不要逐个发精准信号** —— 这类变更整体走 **reset 通道**：

```cpp
// ✅ 推荐写法（规范顺序见 navtreemodel.h 的文件头注释）
std::vector<GuiBase*> oldChildren = collectChildren(parent);

view->setUpdatesEnabled(false);                  // 可选：这一轮会整页重排，先冻住重绘

model.beginFullReset();                          // ① beginResetModel

    for (GuiBase* c : oldChildren) {
        P.notifyRemove(parent, c);               // ② 讣告（可选，见下"为什么可以不逐个报"）
        destroyNode(c);                          //    按各政体的销毁规矩删数据
    }
    P.prune();                                   // ③ 清掉清空后残留的僵尸账页（rebind 内部也会 prune，写在这里更直观）
    for (int i = 0; i < N; ++i) {
        attachNewChild(parent, i);               // ④ 重建新孩子（addSubDataGroup / QObject parenting / addTreeChild）
    }
    P.rebind();                                  // ⑤ = prune + 按谓词重新装全部绑定页（新对象是新地址，必须重装）

model.endFullReset();                            // ⑥ endResetModel + 回收退役组
view->doItemsLayout();                           // ⑦ ★ 必须：reset 之后视图要重排
view->setUpdatesEnabled(true);
```

**为什么可以不逐个 `notifyRemove`**：`rebind()` 内部先调 `prune()`，那是**卫生边界**，
会对每个账页做"枚举 vs 上次快照"比对，漂移的当场置脏重算 —— 也就是**全量自愈**。
代价是：在 `endFullReset()` 之前，投影是**陈旧的**，**别在这中间去读它**
（不要 `childCount`、不要 `model.rowCount()`）。

**为什么必须 `rebind()` 而不是 `prune()`**：`rebind` = `prune` + 按谓词重新装页。
全量重建后**新对象是新地址**，只有 `rebind` 能把"哪些父亲该有投影"重新认出来。

**视图状态（展开 / 选中）**：`endResetModel()` 按 Qt 语义会**丢弃全部视图状态**。
要保住展开态，按 `interactive_demo` 的做法：reset 前收集"展开节点的指针集合"，
reset 后遍历活投影树，只对"活树 ∩ 之前展开"的节点 `setExpanded(true)`。

**顺带一条性能纪律**：`prune`/`rebind` 是**全树 DFS**（约 120 ms / 百万节点）。
别放进每帧或每行绘制路径；也别用 `N × install` 代替（`install` 内嵌一次全树 prune，
实测 1 万父逐个 ≈ 20 分钟，而 `bindSpec + rebind` 一次 0.5 s）。

## 4. 场景：**释放一个父节点下的所有子结点（不重建）**

```cpp
model.beginFullReset();                          // 整页清空同样走 reset 通道
    for (GuiBase* c : std::vector<GuiBase*>(collectChildren(parent))) {
        P.notifyRemove(parent, c);               // 讣告：c 名下的组会进延迟回收队列
        destroyNode(c);
    }
    // P.invalidate(parent) 可省：notifyRemove 内部已经 invalidate(parent) 了
model.endFullReset();                            // 此刻 parent 页重算 ⇒ 0 行；退役组一并回收
view->doItemsLayout();
```

引擎这边**你不需要手动管理任何组**：

| 你以为要做的 | 实际发生 |
|---|---|
| 「把那个组的对象删掉」 | 组是**规则的产物**：没有节点再给它的 key 出票 → 它在重算中被淘汰 |
| 「清掉组的成员指针」 | 组**不存成员**：成员 = 规则 × 父亲当前活列表，现场解析，删数据即自动失效 |
| 「通知视图那一行没了」 | `beginFullReset/endFullReset` 让全部坐标失效，视图整页重排 |
| 「回收淘汰掉的组对象」 | 引擎延迟释放（`m_retired`），由 `endFullReset` 自动兑现 |

**只想"从视图里拿掉"，不想删数据** —— 那是 `filter`，不是删除：

```cpp
spec.filter = [](GuiBase* n) { return dynamic_cast<PartObject*>(n) != nullptr; };
model.beginFullReset();
P.install(parent, spec);      // 被滤掉的节点移出投影，rowOf 返回 -1 —— 数据一动不动
model.endFullReset();
view->doItemsLayout();
```

## 5. 场景：**精准删除一个节点（只动一行，别整页重排）**

```cpp
// 事前坐标协议：坐标必须在 victim 死【之前】取
GuiBase* dyingGroup = cascadeTarget(P, victim);          // 级联预判：删它会让哪个组一起蒸发？
GuiBase* sigParent  = dyingGroup ? P.parentOf(dyingGroup) : P.parentOf(victim);
int      sigRow     = dyingGroup ? P.rowOf(dyingGroup)    : P.rowOf(victim);
if (sigRow < 0) {
    // 被过滤 / 不在投影树上 → 视图本来就没有这一行：不发信号，走 invalidate 即可
    P.notifyRemove(dataParent, victim);
    destroyNode(victim);
    return;
}

model.beginRowRemoval(sigParent, sigRow);                // ① 括号（此刻会发 rowsAboutToBeRemoved）
    P.notifyRemove(dataParent, victim);                  // ② 必须在 delete victim 之前
    destroyNode(victim);                                 // ③ 删数据
model.endRowRemoval();                                   // ④ endRemoveRows + 按水位回收本窗口退役的组
```

**为什么顺序不能换**（这是最容易被写错的一处）：

1. **先取坐标**：`notifyRemove` 会把父页置脏；一旦置脏，**任何后续坐标查询都会触发重算**，
   而死者的行已经没了 —— 那时再 `rowOf(victim)` 拿到的是错的（甚至 -1）。
2. **`notifyRemove` 必须在 `delete` 之前**：它对**正在死的对象**做讣告（只比较指针、不解引用）。
3. **信号发在哪一行？** 若目标组的**最后一个成员**被删，整个组会蒸发 ——
   视图里消失的是**组那一行**，所以信号必须报在组的位置。
   `cascadeTarget()` 就是算这个的；**多层嵌套下它会向上找到最外层**那个也会蒸发的组
   （只判一层会让外层组行消失却无信号 ⇒ 视图与模型失步）。三个 demo 共用这一份实现。

## 6. 场景：**属性变更（材质 / 名字 / 可见性）**

```cpp
part->setMaterial("Alum");     // 数据侧改完
P.invalidateNode(part);        // ★ 必须。它内部 = invalidate(part 的投影父亲所在页)
```

> ⚠ **没有兜底**（见 §2）。漏一次，分组结果就一直错到下一次 `install`/`rebind`/reset。
> 建议把"改属性"的地方收口成一个函数（像 `interactive_demo` 的 `createAndAttach` 那样），
> 在收口点统一调 `invalidateNode`，避免散落各处漏掉。

## 7. 场景：**换分组规则 / 多条规则并存**

```cpp
// 一次性换规则（这一页以后按"手动 Spec"对待，不再受绑定影响）
model.beginFullReset();
P.install(parent, newSpec);          // install = "设定这一页的投影定义"，幂等
model.endFullReset();
view->doItemsLayout();

// 或者声明式（跨全量重建自动重生）—— 规则锚在【谓词】而不是指针
P.bindSpec(binding);                 // 同 id 覆盖；内部立刻 rebind
P.unbindSpec("parts-by-material");   // 解绑不拆已装投影；要立即拆用 uninstall
P.rebind();                          // 全量重建后手动触发重装
```

**"多条规则并存"= 一个 `GroupRule` 内部组合**（引擎每页只有一个分组函数）：

```cpp
GroupRule manual  = ...;                     // 你的手工组（按名字命中）
GroupRule factory = GroupRules::byKey(...);  // 按属性自动分组
spec.grouping = [manual, factory](GuiBase* n) -> std::optional<GroupTicket> {
    if (auto t = manual(n))  return t;       // 手动优先
    if (auto t = factory(n)) return t;
    return std::nullopt;                     // 逃生口：不分组，留直属
};
```

**两个必须知道的语义**：

- **组的身份 = `key`**。同 key 复用同一个组对象 ⇒ **展开/选中状态跨重算存活**；
  换了 key 就等于换了一个组（旧组会被淘汰回收）。
- **key 必须按"页"唯一**。引擎是进程级单例、keyspace 全局共享：
  两个不同的父亲各自建同名组，会按 key 互相"抢"（`matchReusable` 按 key 配对），
  被抢输的一方连同它的成员表一起被清掉。多根/多文档场景下，**用"页名/根名"做 key 前缀**
  （`interactive_demo` 的 `stressRuleFor` 就是这么干的）。

## 8. 场景：**搜索 / 临时显示被过滤的节点**

`filter` 是 `ProjectionSpec` 的一部分，所以"掀开过滤器"= 换一个 Spec：

```cpp
auto buildSpec = [&](bool showAll) {
    ProjectionSpec s;
    s.filter = [showAll](GuiBase* n) {
        return showAll || isRelevant(n);        // 搜索态：不滤
    };
    s.grouping = ...; s.less = ...;
    return s;
};

model.beginFullReset();
P.install(root, buildSpec(/*showAll=*/true));
model.endFullReset();
view->doItemsLayout();
// 想定位某一行：P.rowOf(node)（<0 = 不在投影树上，比如仍被过滤掉了）
```

被过滤的节点 `rowOf()` 返回 **-1**、`parentOf()` 会给自然父亲 —— 用它判断"这一行现在可不可见"。

## 9. 场景：**多文档 / 多根**

```cpp
P.registerRoot(docA.root);       // 每个根都要注册（prune/rebind 从根出发做可达性剪枝）
P.registerRoot(docB.root);

// 跨根定位必须自限定 —— 因为 locate 谓词会在【所有页】上被问
auto topOf = [](GuiBase* n) {                  // ← 自包含的小工具：沿展示父亲上溯到根
    GuiBase* p = n;
    while (p) { GuiBase* q = p->parentForTree(); if (!q) break; p = q; }
    return p;
};
binding.locate = [rootA, topOf](GuiBase* n) { return topOf(n) == rootA && isPart(n); };

// 关闭一个文档
P.unbindSpec("docA-parts");
P.uninstall(docA.root);          // 或依赖 prune 的可达性剪枝
P.unregisterRoot(docA.root);     // ★ 必须在 delete 之前：留下死根会让 prune 解引用它
delete docA.root;
P.collectGarbage();
```

## 11. 接口速查（该调 / 不该调）

| 目的 | 调 | 前提 / 注意 |
|---|---|---|
| 装 / 换投影定义 | `install` / `apply` | **必须在 reset 括号内**（`prune` 内嵌其中） |
| 声明式规则（跨重建） | `bindSpec` / `unbindSpec` / `rebind` | 同上 |
| 拆掉整页投影 | `uninstall` | 同上；**立即**释放该页的组 |
| 精准删除一行 | `beginRowRemoval` → `notifyRemove` → 删 → `endRowRemoval` | 见 §5 的顺序 |
| 整页换血 | `beginFullReset` → wipe → rebuild → `rebind` → `endFullReset` → `doItemsLayout` | 见 §3 |
| 数据变了 | `invalidate` / `notifyRemove` | 属性变更用 `invalidateNode`（**无兜底**） |
| 读 | `childCount` / `child` / `parentOf` / `rowOf` | 随时可调；可能触发惰性重算 |
| 观测 | `structRev` / `retiredCount` / `retiredHighWater` / `memoryBreakdown` | 不改变任何状态 |
| 回收 | `collectGarbage`（reset 后）/ `collectGarbageSince(mark)`（removeRows 后） | 模型层已自动调用；手写时要自己守时机 |

**别在帧循环里调**：`prune` / `rebind`（全树 DFS，~120 ms/百万节点）。
**别用 `N × install` 批量装配**：用 `bindSpec + rebind`（20 分钟 vs 0.5 秒）。

## 12. 现象 → 根因 速查（给现场排查用）

| 现象 | 最可能的根因 | 怎么确认 |
|---|---|---|
| 内容跟数据对不上，过一会儿又对了 | 漏了 `invalidate` / `notifyRemove` | 开 `setParanoidChecks(true)`，stderr 会点名是哪个 owner |
| 改了材质 / 名字，分组不更新 | 漏了 `invalidateNode` | **没有兜底**，只能查所有改属性的调用点 |
| 视图多一个空组行 | 规则输出自相矛盾（"没有任何节点属于 A" 与 "A 属于 B" 同时成立） | Debug 下 stderr 点名"丢弃了 N 个空壳组" |
| 展开大树卡住 / 交互卡 | 在帧循环里调了 `prune`/`rebind` | 全树 DFS；把它移出热路径 |
| 删除后视图行数与模型对不上 | 信号坐标报错（尤其**级联蒸发**时没报在组那一行） | 用 `cascadeTarget()`；多层嵌套必查 |
| 每次删除后展开态全丢 | 走了 reset 通道（`endResetModel` 丢弃全部视图状态） | 换精准删除通道，或按 §3 恢复展开态 |
| Debug OK、Release 行为不同 | Release 下 `paranoid` 默认关（漏通知不再点名，只静默陈旧） | 首发把 `setParanoidChecks(true)` 打开 |
