> 2026-10-05 完成。本文档是**结论与证据**，不是待办快照。
> 目标：验证 TreeProjection 能否扛住生产环境预估的**百万节点**量级。

## 二、最终实测（Release，3 次运行取中位；同机）

| 场景 | 本轮优化前 | **最终** | 提升 |
|---|---|---|---|
| build-1M（数据侧建树，引擎无关） | 108 ms | **111 ms** | — |
| **cold-bind**（bindSpec+rebind 批量装 1 万父） | 1196 ms | **495 ms** | **2.4×** |
| rowcount-cache-hit（模型 rowCount 热路径） | 700 ns | **576 ns** | 1.2× |
| **parentOf+rowOf**（模型 parent()/indexFor） | 3400 ns | **2190 ns** | **1.55×** |
| model-full-dfs（111 万 index 全量遍历） | 875 ms | **761 ms** | 1.15× |
| delete-1k+revalidate（增量删除） | 64 µs | **56 µs** | 1.15× |
| **rebuild-channel**（wipe+重建+prune冷+walk） | 1717 ms | **932 ms** | **1.84×** |
| wide-install-200k（单父 20 万孩子 × 100 组） | 695 ms | **198 ms** | **3.5×** |
| wide-rowOf（宽亲病态成员定位） | 367 µs/次 | **185 µs/次** | 2× |
| **prune-1M**（全树可达性剪枝） | 532 ms | **120 ms** | **4.4×** |
| install-loop（反例：逐个 install） | 528 ms/次 | **122 ms/次** | 4.3× |
| bench TOTAL | 5572 ms | **~2600 ms** | **2.1×** |
| 峰值工作集 WS | 304 MB | **300 MB** | 持平 |

（"优化前"= 本轮改动之前的引擎，即上一版交接文档记录的数。）

### 关键结论（百万节点）

- **全量重建通道 ≈ 0.93 s**（wipe 100 + 重建 66 + prune冷 606 + walk 154）
- **全树一次性展开 ≈ 0.76 s**（111 万 index）
- **冷启动批量装 1 万个父的投影 ≈ 0.50 s**
- **交互级操作 µs~ms**：单次查询 2.2 µs、增量删除 56 µs
- **峰值内存 300 MB**（1M 数据节点 166 MB + 10 万组 + 引擎账本 ≈ +134 MB）

### 账本内存分解（`bench mem` 实测；做内网内存预算用这张表，别用估值）

| 项 | 条目数 | 字节 |
|---|---|---|
| `m_byParent` 本体 + 桶 | 10,100 页 | 2.7 MB |
| 每页 `spec` | — | 2.4 MB |
| `lastLive`（缓存钥匙） | 1,010,100 指针 | 7.7 MB |
| `flat`（投影序列） | 1,010,100 指针 | 1.1 MB |
| `p.members`（组→成员） | 100,000 组 / 1,000,000 指针 | 13.7 MB |
| **`memberToGroup`（成员→组）** | **1,000,000 条** | **54.1 MB（占账本 61%）** |
| `p.groups` + `m_groupOwner` | 100,000 | 6.6 MB |
| **引擎账本小计** | | **88.4 MB** |
| （另：`TreeGroup` 对象本体） | 100,000 | 9.2 MB |

换算：**引擎账本 ≈ 88 MB / 百万被投影节点**（约 88 B/节点），加上组本体约 98 B/节点。
工作集比这个数高约 40 MB，差值来自分配器碎片 + prune 的临时 `PtrSet`（16 MB，事后释放）。

**`memberToGroup` 是唯一的内存大头，且它是"可选的"**：它只是 `p.members` 的反向索引，
唯一用途是 `parentOf` 的 O(1) 查与 `buildFlat` 的代表上溯。三条路：

1. **接受**（当前默认）。88 B/节点 对百万节点 = 88 MB，在现在动辄几个 G 的客户端里不是问题；
2. **换扁平开放寻址表**（复用 `ptrset.h` 的思路，键值各 8 B、负载 0.75）→ 约 32 B/条，
   省 ~22 MB（账本的 25%）。代价：多一个容器 + 改一处查找，收益有限；
3. **删掉它**，`parentOf` 改为扫 `p.members` 的各组。窄亲（≤百成员）毫无损失，
   但 **宽亲会退化**（20 万孩子 × 100 组 → 每次 parentOf 扫 20 万次指针比较）。
   **只有在确认自己的树"没有宽亲"时才可选**。

## 三、优化清单（全部**语义保持**，唯一例外是 §3.6 的纪元闸门，它带显式前提）

### 3.0 先立方法：A/B 归因，别猜

`bench pbreak` 与 `bench cold,query` 的输出是本轮所有决策的依据。
最关键的一张表（1M 节点）：

```
[AB] A raw-dfs-only              11 ms   (11 ns/节点)   ← 数据侧地板价:走树本身几乎不要钱
[AB] B raw-dfs + unordered_set  255 ms  (255 ns/节点)  ← 旧实现的去重集账
[AB] C raw-dfs + PtrSet          50 ms   (50 ns/节点)   ← 现在的去重集账
[AB] D engine prune()           124 ms                 ← 引擎实测
```

**A 只有 11 ms**：任何"prune 太慢"的抱怨，第一反应都该是"多出来的 113 ms 花在哪"，
而不是去优化 DFS 本身。下面四条改动全部由此而来。

### 3.1 去重集换 `PtrSet`（prune −4.4× 的主因）

新增 `ptrset.h`：指针值专用的**开放寻址**集合（线性探测、容量幂二、2 倍翻倍、零节点分配）。

为什么 `std::unordered_set` 在这里是灾难（255 ns/节点 vs 50）：

1. 每次 insert 一次 `operator new`（节点式存储）—— 百万次 malloc；
2. 扩容是逐级小步长（1→3→7→17…），每次 rehash 全量重插，且 rehash 后元素哈希值不能缓存；
3. 指针低 4 位恒为 0（malloc 16 字节对齐），默认哈希近似恒等，桶分布不可控。

⚠ **踩过的坑**：位图/哈希若允许"按需扩容"，指针哈希接近 2^64 时容量计算会溢出成天文数字
（`std::vector::resize` 抛 `length_error` → `abort()`）。本工程的提示位图因此**定长不扩容**。

### 3.2 `prune()` 空账本短路（cold-bind 的一半）

`m_byParent` 空 ⟹ 没有任何可剪的对象 ⟹ 整个可达性 DFS 是纯白走。
冷启动首装（`bindSpec` 第一次生效）正是这个状态。
判据写成 `m_byParent.empty() && m_groupOwner.empty()`——不变量是
"组由账页创建、`dropProjection` 双向成对维护"，所以账本空必然组表也空。

### 3.3 三张热查找表 `std::map` → `unordered_map`

`[Q] lookup 10k keys: std::map 96 ns/find | unordered_map 17 ns/find`

红黑树每一级都是一次可能 cache miss 的指针追逐。三张表都在读侧四件套的**每一步**上：

| 表 | 规模（本工程树形） | 谁在查 |
|---|---|---|
| `m_byParent` | 1 万页 | childCount/child/parentOf/rowOf/两个 DFS 每一步 |
| `m_groupOwner` | **10 万组** | `freshMembers`（childCount/child/两个 DFS/rowOf 都调） |
| `memberToGroup` | 100 万条成员映射 | parentOf 每层下钻、buildFlat |

换过去是安全的，两点理由都写进了头文件注释：

- **引用稳定性**：标准保证 unordered 容器 rehash **只失效迭代器，不失效元素引用与指针**
  （节点式容器）。`revalidate` 一路持有的 `Projection&` 因此在任何插入下都安全。
- **无序性无害**：全库对 `m_byParent` 的遍历只有 4 处（析构清账 / liveGroupCount 求和 /
  prune 收 stale / hasProjection），全是顺序无关的；`memberToGroup` 只按值查找。
  `p.members` 保持 `std::map` 未动（它的遍历顺序参与组账本构建，语义上更保守）。

配套：`memberToGroup` 建表前 `reserve(精确规模)`。不预留会经历一串 rehash
（每次都是"重建整张桶数组 + 全量重插"），实测让峰值 WS 多吃 60 MB。

### 3.4 存在性提示位图（剪枝的"否定探测"太贵）

prune/walkBindings 要走遍全树，对**每个节点**问两个问题："你有账页吗？"（哈希探测，cache miss）
+"你是组吗？"（`dynamic_cast`，RTTI 走链）。百万节点里真正有账页的约 1 万、是组的约 10 万
—— **89% 的节点两个答案都是"否"，却付了 60~80 ns/次的探测成本**。

`m_pageHint` / `m_groupHint` 各一张**定长 2^23 位（1 MB）**位图，把"答不上来"变成一次位测试。

**能用它的前提是失效方向安全**：位图**只置位、从不清除**，所以只可能往"多算"的方向撒谎
（白做一次探测，无害）。唯一危险是**漏置位**——账页真存在却没提示 → 跳过它 → 它的子树不可达
→ **活着的账页被当成僵尸删掉**。所以置位义务收敛到两个唯一创建点：

- 账页：`Projection& projection(GuiBase*)`（头文件里已注明"任何将来新增的建页路径必须走这里"）；
- 组：`revalidate` 里唯一的 `new TreeGroup`。

⚠ **另一条纪律**：这道门控**绝不能用来跳过 `walkBindings` 的绑定谓词**。
`locate` 必须对每个活数据节点求值，否则"谓词命中但没账页"的节点永远装不上投影——
声明式绑定的全部意义就没了。（实现时就踩过：门控放在谓词之前 → 五个 demo 全崩。）

### 3.5 查询纪元：一次操作内同一账页只校验一次

`parentOf` 要下钻查 `memberToGroup`，`rowOf` 随后又要扫 `flat`，两次都调 `revalidate`；
组页更甚——组 `revalidate` 内部还要回头校验 owner。同一次查询里同一页被校验 2~3 次。

`m_queryEpoch` + `Projection::checkedAt`：每个公开操作入口（读侧四件套 + install/apply/
prune/rebind/refresh/bindSpec）开一个 `EpochScope`，**只有最外层**才递增纪元
（`rowOf` 内部调 `parentOf`，二者必须共享同一纪元，否则优化归零）。
`revalidate` 第 0 步若 `checkedAt == 当前纪元 && valid` 就直接返回。

**这个优化的前提必须写清楚**：安全性依赖"数据侧变更必然经过引擎 API，或与引擎无交互"——
引擎惰性发现变更的唯一途径就是枚举活列表，而纪元只在一次操作内有效，
一次操作内单线程同步语义下数据侧不可能被改。**若你们的模型跨线程/异步改数据树，禁用它**
（删掉 `EpochScope` 即可，行为完全不变，只是慢一点）。

配套：`installInternal` / `refresh` 强制重算时必须把 `checkedAt` 一起清零——
否则 `valid=false` 仍会被纪元闸门短路。

### 3.6 bench 自身修过的坑（别误当引擎 bug）

- 材料索引 `(rebuilt+f)%10` 步进 2 只出 5 种材料（曾冤枉引擎"组数减半"）；
- 期望值应为 P 层 × 10 = 100,000（A 层孩子是 P、无材料 → 0 组是**正确**行为，不是丢组）；
- `childCount` 调用本身会把空组淘汰——`after-rebuild(pre-rebind)` 显示 0 组是 dump 自己触发的
  revalidate，属正常语义；
- deep 场景拆链必须**迭代**（`~GuiBase` 连坐析构是递归的，10 万深链 `delete root` 会爆 1 MB 栈
  ——**这是冻结架构自带的属性，与引擎无关**，生产树深 <100 无虞）；
- teardown 清僵尸要挂临时探针根再 prune（`m_roots` 空时 `prune` 直接 return，设计如此）。

## 四、生产纪律（数据坐实，不是建议）

1. **批量装配走 `bindSpec` + `rebind`，绝不 N×`install`。**
   `install` 内嵌一次全树 `prune`。1 万个内部节点逐个 install ≈ **20 分钟**（优化前 1.6 小时）；
   走绑定一次 ≈ **0.5 s**。
2. **`prune` / `rebind` 是全树 DFS（~120 ms/百万节点），别放进每帧或每行绘制路径。**
   交互操作（查/删）走的是增量校验（µs 级），两者别混。
3. **超深链注意 `~GuiBase` 的递归连坐析构。**
   引擎的 DFS 全部显式栈迭代化（10 万深链已实测不爆栈），但**数据类析构仍是递归的**：
   深度 >3 万级时 `delete root` 本身会爆栈。真有超深链就调 `/STACK` 链接器储备，
   或自底向上摘除+删除。这是类结构属性，改引擎解决不了。
4. **内存敏感的话**：见 §二 的账本分解表。引擎账本 ≈ **88 B/被投影节点**，
   大头是 `memberToGroup`（54 MB / 61%）。三条路（接受 / 换扁平表省 25% / 删掉但宽亲会退化）
   那里都写了，按自己的树形选。

## 五、还剩什么（都已定性为"可接受"，不必再磨）

- **prune 地板价 120 ns/节点**：`A=11ms`（走树）+ `C=50ms`（去重集记账）已占 61 ms，
  引擎自身只剩 ~60 ms（1 万页的 revalidate + 账本比对，是真实工作量）。再压要动数据结构，
  收益不足风险有余。
- **`rowcount-cache-hit` 576 ns**：100 次虚接口枚举是**政体数据侧的成本**，
  引擎这边已经是零分配命中，没有可省的。
- **`model-full-dfs` 761 ns/index**：模型的 index/parent 三要素 + 虚接口，不可再压。
- **`parentOf` 850 ns**：`[Q]` 拆分显示大头已从查表结构转移到"活列表校验 + 下钻链"，
  属设计固有的成本。
